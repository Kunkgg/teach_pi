Lesson 0004 · Runtime choices

先诊断瓶颈，
再切模型

本课只建立一个操作习惯：把“能力不够”“推理不够”和“上下文太重”分开处理，形成你的最小切换策略。

约 15 分钟一次运行时切换暂不改默认设置

1. 三个旋钮解决三类问题

Model

决定能力边界、输入类型、上下文窗口、速度与计费方式。用 /model 或 Ctrl+L 选择。

Thinking

控制当前模型的推理 effort/budget。用 /thinking 或 Shift+Tab 切换；模型支持的档位可能不同。

Context

是本次请求实际可见的系统提示、活动路径、工具结果与摘要。Footer 显示当前用量。

Session history

是 JSONL 中保存的完整树。它可能比当前 model context 更完整；二者不要混淆。

Pi 的 model options 把 model 与 thinking 分开；自动 compaction 则在 context 超过 contextWindow - reserveTokens 时处理旧消息。它们不是同一个“质量”开关。

最短诊断法：模型会做但想得不够深 → 调 thinking；模型能力或输入类型不匹配 → 换 model；历史太长 → compact；任务已经无关 → new/fork。

2. 不要把 thinking 当“免费变聪明”

Thinking level 是请求模型投入的推理等级，而不是跨模型统一的刻度。Pi 暴露 off、minimal、low、medium、high、xhigh、max；但当前模型可以只支持其中一部分。官方 Thinking Level Map 说明了不支持的档位会被隐藏、跳过或限制到可用范围。

任务类型起始动作不要做
事实明确的快问、短转换当前快速候选 + low每次都直接 high
常规跨文件实现实现基线 + medium一遇阻力就轮换模型
架构取舍、疑难诊断、高风险变更先 high；能力不匹配再换模型同时换模型、thinking 和上下文

一次只改一个变量，你才知道改善来自哪里。模型名字中的 “flash”“pro”等只适合提出候选假设，不构成质量证据。

3. Context 不是越满越值得保留

长上下文可能包含已经失效的方案、大段工具输出和与当前任务无关的讨论。Pi 默认保留最近约 20k token，并为下一次响应预留 16,384 token 后再自动压缩；具体值见 Compaction settings。

  • 关键约束、决定和状态应先写进代码、测试、ADR 或学习记录。
  • /compact 是有损摘要，不是清空 session；原始历史仍在 JSONL 树中。
  • 切到 context window 不同的模型后，同一段历史占窗口的比例也会变化；看 footer，而不是凭消息条数猜。
动手：建立一份暂不保存的三档策略
  1. 在 Pi 中运行：
    !!printf '%s/%s · thinking=%s\n' "$PI_PROVIDER" "$PI_MODEL" "$PI_REASONING_LEVEL"
    双感叹号让结果只显示给你，不送入模型上下文。再看 footer 的 context 使用量。
  2. 按 Shift+Tab 切换 thinking，观察 editor 边框；再次运行上面的隐藏命令确认等级，停在 low。
  3. 按 Ctrl+P 在 scoped models 中前进一次，再按 Shift+Ctrl+P 返回。当前配置已有 11 个 scoped models，无需新增。
  4. 用 /model 查看模型详情，再取消；用 /thinking 查看当前模型真正支持的档位，再取消。
  5. 把 thinking 恢复到本次任务需要的等级。这次不要按 Ctrl+S：先验证策略，再保存默认值。
  6. 给我发送下面三行，并按你的偏好改写： 
    快问：deepseek/deepseek-v4-flash + low（候选）
实现：deepseek/deepseek-v4-pro + medium（基线）
难题：先提高实现基线的 thinking；仍卡住再用 openai-codex/gpt-5.6-sol + high（候选）

反馈标准不是“哪个模型最强”，而是你能否说明每次调整针对的是能力、推理投入，还是上下文负担。随后用三次真实任务记录延迟、返工与结果，再决定是否保存默认值。
